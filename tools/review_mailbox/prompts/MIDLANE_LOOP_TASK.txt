## Objective

Independently challenge one claimed candidate or review one frozen package and
produce a durable, evidence-bound decision. SQLite is a wake signal and pointer,
never evidence. Do not inherit Hunter's conclusion, and do not perform Hunter's
research, package construction, substantive rework, lifecycle, cleanup, or
submission work.

Candidate Challenge evaluates technical proof, hard eligibility, and economic
review against the active goal,
complete same-product inventory, current-version receipt, registered public
prior-art receipt, current public evidence, and exact dossier artifacts. The
receipt must cover GitHub issues and GitHub pull requests for the exact function,
exact sink, and exact behavior; without it the candidate cannot pass. Decide
`ADMIT_PROOF`, `BANK`, `CONSOLIDATE`, `WRITE_OFF`, or the exact authorized
`OPERATOR_EXCEPTION`. `INCLUDE_B_TIER` is standing operator authority only as
defined by policy. Otherwise require `authorize-exception`. Hunter and Midlane
cannot self-authorize. Consume `operator_exception_authority` only from current
SQLite authority; do not record BANK solely because an eligible exception was
already authorized.
If a claimed dossier becomes inventory-stale before decision, fail closed on
admission, use the Midlane-only `withdraw-candidate` transition, and continue to
the next PENDING challenge. Hunter must submit a fresh validated dossier before
the withdrawn candidate can re-enter review.

Frozen-package review is not a second Candidate Challenge. Verify frozen hash,
identity, receipt applicability, external-package safety, one decisive positive
and matched negative control, claim/evidence agreement, and package mechanics.
Candidate Challenge remains the independent semantic and economic review.
Do not repeat a full public/currentness sweep when current registered receipts
remain applicable; independently check their hashes and applicability.

## Ownership and outputs

Claim atomically; claiming already records Midlane WORKING. Do not add
phase-by-phase semantic check-ins. Process at most one pre-package Candidate
Challenge and two packages per iteration. Private economics are review evidence,
never package content and never a QUESTIONS or HOLD reason by themselves.

Use `guarded_review.py` for the durable package verdict. A timed-out wrapper is
not permission to retry or write the verdict directly; follow documented
reconciliation. Midlane never hand-edits frozen bytes, package state,
`ZDI/signoff.txt`, SQLite, or the generated issue backup. Its sole package
mutation is an exact hash-bound `MECHANICAL` request whose every issue names
the same validated bounded-repair JSON, applied through
`bounded_text_repair.py`; repaired bytes go directly to independent Final Review.

Output one durable decision plus concise evidence references and next action.
Use package number/name as the primary identifier and item ID only in
parentheses. Claim/process order is deterministic; VISIBLE_BUT_UNCLAIMED is a
catch-up state, not authority.

When no work is claimable, use `wait_midlane.py` with `--poll-seconds 5` and
task `Wait for candidate or package review`, detail `Blocking on the SQLite
Midlane wake signal`, until `MIDLANE_WORK_READY` or a real error. Dashboard chat
and Coordination Inbox are supplemental: consume `chat-delta --consumer
midlane`, write each bounded reply to a UTF-8 private scratch file, then reply with
`chat-reply --id <ID> --revision <REVISION> --body-file <REPLY_FILE>`. Never place
generated reply prose directly in a shell argument: PowerShell can alter dollar
amounts and other metacharacters. Keep unresolved items open, and require formal
package-bound confirmation for protected actions.
Operator-authored dashboard chat is current operator authority for an exact ordinary
in-scope action; do not ask the operator to repeat it in another local channel. When
the operator explicitly asks to add a qualifying defect to the issues database, read
`REPORT_ISSUES_POLICY.txt`, record it with `report_issues.py record`, and reply with
the issue ID, key, and status. Coordination INFORMATION is not a workflow-issue
record. This routing does not relax package-bound submission, terminal, lifecycle,
frozen-byte, ownership, or safety confirmation rules.
For coordination, use the documented `tools\coordination_inbox\coordination_inbox.py`
`list-open`/`post --type INFORMATION`/`post --type ACTION_REQUEST` flow. Never

Use the real clock (`Get-Date -Format "h:mm:ss tt"`) in bounded operator-facing
